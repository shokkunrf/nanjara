## 1. 正常系テストケース

### TC-001: preload()がバックグラウンドロードを開始する

- **テスト名**: preload呼び出しでOpenCV.jsの動的importが開始される
  - **何をテストするか**: `preload()` 呼び出し時に `@techstark/opencv-js` の動的 `import()` が実行されること
  - **期待される動作**: `preload()` は同期的に返却し、内部でバックグラウンドロードが開始される
- **入力値**: なし（パラメータなし関数）
  - **入力データの意味**: preload() はパラメータを持たない関数
- **期待される結果**: `@techstark/opencv-js` の動的 `import()` が1回呼ばれる
  - **期待結果の理由**: preload() の責務はバックグラウンドロードの開始であり、import() の呼び出しが確認できればよい
- **テストの目的**: preload() がWASMの先読みロードを正しく開始することの確認
  - **確認ポイント**: vi.mock() で `@techstark/opencv-js` をモックし、import() が呼ばれたことを検証
- 🔵 要件定義のpreload()仕様（セクション2）およびTASK-0005タスク定義に基づく

### TC-002: ensureLoaded()がロード完了後にresolveする

- **テスト名**: ensureLoaded呼び出しでロード完了後にPromiseがresolveする
  - **何をテストするか**: `ensureLoaded()` がOpenCV.jsのロード完了を待機し、正常にresolveすること
  - **期待される動作**: 内部のロードPromiseが解決された後、`ensureLoaded()` のPromiseもresolveする
- **入力値**: なし（パラメータなし関数）
  - **入力データの意味**: ensureLoaded() はパラメータを持たない非同期関数
- **期待される結果**: Promiseがresolveし、例外が投げられない
  - **期待結果の理由**: ロード成功時はresolveするのが正常動作
- **テストの目的**: ensureLoaded() のロード完了保証機能の確認
  - **確認ポイント**: `await ensureLoaded()` が正常に完了すること。vi.mock() でimportをモックし、resolveするPromiseを返す
- 🔵 要件定義のensureLoaded()仕様（セクション2）に基づく

### TC-003: preload()後のensureLoaded()が即座にresolveする（先読み完了済みフロー）

- **テスト名**: 先読み完了後のensureLoadedは即座にresolveする
  - **何をテストするか**: `preload()` で先読みが完了した後に `ensureLoaded()` を呼ぶと即座にresolveすること
  - **期待される動作**: 先読みが既に完了しているため、追加のロード処理なしで即座にresolveする
- **入力値**: preload() を事前に呼び出し、ロード完了を待ってからensureLoaded() を呼ぶ
  - **入力データの意味**: 使用例パターン1（正常フロー: 先読み完了後に使用）を再現
- **期待される結果**: ensureLoaded() が即座にresolveし、import() は追加で呼ばれない
  - **期待結果の理由**: 先読み済みのPromiseを再利用するため、追加のロード不要
- **テストの目的**: 先読み→使用の基本フローが正しく動作することの確認
  - **確認ポイント**: import() の呼び出し回数が1回のみであること
- 🔵 要件定義セクション4 パターン1、およびキャッシュ要件に基づく

### TC-004: preload()を呼ばずにensureLoaded()を直接呼び出し

- **テスト名**: preload未呼び出しでもensureLoadedが正常にロードして返す
  - **何をテストするか**: `preload()` を呼ばずに `ensureLoaded()` を呼んだ場合、自動的にロードを開始して完了すること
  - **期待される動作**: ensureLoaded() 内部でロードを開始し、完了後にresolveする
- **入力値**: preload() を呼ばずに ensureLoaded() を直接呼び出し
  - **入力データの意味**: エッジケース2（preload未呼び出し）を再現。防御的プログラミング
- **期待される結果**: Promiseが正常にresolveする
  - **期待結果の理由**: preload() はオプショナルな最適化であり、ensureLoaded() 単独でも動作すべき
- **テストの目的**: ensureLoaded() の自立動作（preload非依存）の確認
  - **確認ポイント**: import() が呼ばれてPromiseがresolveすること
- 🟡 要件定義セクション4 エッジケース2に基づく。設計文書に明示なく、防御的プログラミングとして妥当と推測

### TC-005: preload()の戻り値がvoidである

- **テスト名**: preloadはvoidを返す（Promiseを返さない）
  - **何をテストするか**: `preload()` の戻り値が `void`（undefined）であること
  - **期待される動作**: preload() は非同期ロードを開始するのみで、Promiseを返さない
- **入力値**: なし
  - **入力データの意味**: API仕様の確認
- **期待される結果**: `preload()` の戻り値が `undefined` である
  - **期待結果の理由**: 仕様上 `preload(): void` と定義されている
- **テストの目的**: 公開APIのシグネチャが仕様通りであることの確認
  - **確認ポイント**: `typeof preload()` が `undefined` であること
- 🔵 要件定義セクション2・セクション6の公開API仕様に基づく

## 2. 異常系テストケース

### TC-006: ロード失敗時にensureLoaded()がrejectする

- **テスト名**: WASMロード失敗時にensureLoadedがエラーをthrowする
  - **エラーケースの概要**: ネットワークエラー等でOpenCV.jsのWASMダウンロードが失敗した場合
  - **エラー処理の重要性**: ロード失敗を呼び出し元に伝搬し、適切なエラーメッセージ表示を可能にする
- **入力値**: vi.mock() でimportをrejectするPromiseを返すように設定
  - **不正な理由**: ネットワークエラーやWASMコンパイルエラーを模擬
  - **実際の発生シナリオ**: オフライン環境、ネットワーク不安定時、低スペック端末でのWASM対応不足
- **期待される結果**: `ensureLoaded()` のPromiseがrejectし、エラーが伝搬される
  - **エラーメッセージの内容**: import失敗のエラーが適切に伝搬される
  - **システムの安全性**: reject後もモジュールがクラッシュしない
- **テストの目的**: WASMロード失敗時のエラーハンドリング確認
  - **品質保証の観点**: ユーザーにエラーを通知し、再試行の機会を与える
- 🟡 要件定義セクション3 エラー処理要件、セクション4 エッジケース1に基づく。具体的なエラーハンドリング方針は推測

### TC-007: ロード失敗後に再度preload()でリトライ可能

- **テスト名**: ロード失敗後のリトライで正常にロードできる
  - **エラーケースの概要**: 初回ロード失敗後、再度preload() を呼ぶことでリトライが可能であること
  - **エラー処理の重要性**: 一時的なネットワーク障害からの復帰を可能にする
- **入力値**: 1回目のimportはreject、2回目のimportはresolveするようモック設定
  - **不正な理由**: 初回失敗を模擬
  - **実際の発生シナリオ**: ネットワークが一時的に不安定な場合、ユーザーが再撮影→再プレビューで復帰
- **期待される結果**: 2回目のpreload() + ensureLoaded() が正常にresolveする
  - **エラーメッセージの内容**: 2回目はエラーなし
  - **システムの安全性**: 失敗状態がリセットされ、新しいロードが開始される
- **テストの目的**: エラー後のリトライ可能性（状態リセット）の確認
  - **品質保証の観点**: ユーザーが再撮影で復帰できることを保証
- 🟡 要件定義セクション3 エラー処理要件、セクション4 エッジケース1「再度 preload() → リトライ可能」に基づく。リトライ時の状態リセット方式は推測

### TC-008: preload()でロード失敗した場合もensureLoaded()でエラーが伝搬する

- **テスト名**: preloadで開始したロードが失敗した場合、ensureLoadedでエラーが伝搬する
  - **エラーケースの概要**: preload() で開始したバックグラウンドロードが失敗した状態で ensureLoaded() を呼んだ場合
  - **エラー処理の重要性**: preload()は戻り値voidのためエラーを捕捉できない。ensureLoaded()で初めてエラーが検知される
- **入力値**: preload() を呼び出し後、モックのimportをrejectさせ、その後 ensureLoaded() を呼ぶ
  - **不正な理由**: preload() のバックグラウンドロードがネットワークエラーで失敗
  - **実際の発生シナリオ**: プレビュー画面表示中にネットワーク切断、「認識する」タップ時にエラー判明
- **期待される結果**: `ensureLoaded()` がrejectする
  - **エラーメッセージの内容**: import失敗のエラーが適切に伝搬される
  - **システムの安全性**: 呼び出し元でtry-catchが可能
- **テストの目的**: preload()→ensureLoaded() フローでのエラー伝搬の確認
  - **品質保証の観点**: エラーが握りつぶされず、UIでユーザーに通知可能
- 🟡 要件定義セクション4 エッジケース1のフローに基づく。エラー伝搬の詳細は推測

## 3. 境界値テストケース

### TC-009: 複数回のpreload()呼び出しでimportは1回のみ（冪等性）

- **テスト名**: preloadを複数回呼んでもimportは1回しか実行されない
  - **境界値の意味**: 複数回呼び出しは冪等性の境界条件。1回と複数回の境界
  - **境界値での動作保証**: 何回呼んでも副作用は1回だけであること
- **入力値**: `preload()` を3回連続で呼び出す
  - **境界値選択の根拠**: 2回で冪等性確認、3回で安定性も確認
  - **実際の使用場面**: コンポーネントの再マウント時に複数回呼ばれる可能性
- **期待される結果**: `import()` の呼び出し回数が1回のみ
  - **境界での正確性**: 2回目以降は既存のPromiseを再利用
  - **一貫した動作**: 何回呼んでもロード状態が一貫している
- **テストの目的**: preload()の冪等性保証の確認
  - **堅牢性の確認**: 重複呼び出しに対するロバスト性
- 🔵 要件定義セクション3 キャッシュ要件「2回目以降の preload() はキャッシュから即座に返す（冪等性）」に基づく

### TC-010: 複数回のensureLoaded()呼び出しでimportは1回のみ（冪等性）

- **テスト名**: ensureLoadedを複数回呼んでもimportは1回しか実行されない
  - **境界値の意味**: 複数箇所から同時にensureLoaded()が呼ばれるケースの境界
  - **境界値での動作保証**: 同一Promiseを共有し、ロード処理は1回のみ
- **入力値**: `ensureLoaded()` を3回連続で呼び出し（Promise.all）
  - **境界値選択の根拠**: 同時に複数箇所から呼ばれるパターンの模擬
  - **実際の使用場面**: 複数コンポーネントが同時にensureLoaded()を呼ぶケース
- **期待される結果**: 全てのPromiseがresolveし、`import()` の呼び出しは1回のみ
  - **境界での正確性**: 同一Promiseを共有している
  - **一貫した動作**: 全呼び出し元が同じ結果を得る
- **テストの目的**: 複数同時呼び出し時の冪等性とPromise共有の確認
  - **堅牢性の確認**: 競合状態が発生しないこと
- 🔵 要件定義セクション3 キャッシュ要件、セクション4 エッジケース3「複数箇所から同時に呼び出し」に基づく

### TC-011: ロード完了後のensureLoaded()は即座にresolveする

- **テスト名**: ロード完了後のensureLoadedは追加ロードなしで即座にresolveする
  - **境界値の意味**: ロード状態の「ロード完了」と「未ロード」の境界
  - **境界値での動作保証**: ロード完了状態でのensureLoaded()は即座に返る
- **入力値**: `preload()` → ロード完了を待機 → `ensureLoaded()` を呼ぶ
  - **境界値選択の根拠**: ロード完了という状態遷移後の振る舞い確認
  - **実際の使用場面**: 2回目の撮影（パターン3: キャッシュ済みフロー）
- **期待される結果**: ensureLoaded() が即座にresolveし、追加のimport()は呼ばれない
  - **境界での正確性**: キャッシュされたPromiseをそのまま返す
  - **一貫した動作**: 初回と2回目以降で結果が同じ
- **テストの目的**: キャッシュ済み状態での即時返却の確認
  - **堅牢性の確認**: 状態遷移後の安定動作
- 🔵 要件定義セクション4 パターン3「キャッシュ済みフロー」に基づく

### TC-012: preload()とensureLoaded()の同時呼び出し

- **テスト名**: preloadとensureLoadedを同時に呼んでもロードは1回のみ
  - **境界値の意味**: preload()とensureLoaded()が同一タイミングで呼ばれる競合条件
  - **境界値での動作保証**: 内部状態の競合なく正常にロード完了する
- **入力値**: `preload()` と `ensureLoaded()` をほぼ同時に呼び出す
  - **境界値選択の根拠**: タイミングの境界（同時呼び出し）
  - **実際の使用場面**: 高速操作で即座に「認識する」ボタンをタップした場合
- **期待される結果**: ensureLoaded() のPromiseが正常にresolveし、import()は1回のみ
  - **境界での正確性**: 同一Promiseを共有
  - **一貫した動作**: 呼び出し順序に関わらず結果が一貫
- **テストの目的**: 同時呼び出しでの競合状態の不在確認
  - **堅牢性の確認**: Race condition がないこと
- 🔵 要件定義セクション3 キャッシュ要件「同時に複数箇所から呼ばれても、ロード処理は1回のみ実行」に基づく

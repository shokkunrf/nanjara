### Q6: 斜め・縦配置への対応

**質問日時**: 2026-03-14
**カテゴリ**: 技術選択
**背景**: Q2で横一列前提としたが、以下の課題が判明した:
- 片手撮影では±15°以上の傾きが発生しうる
- パイが縦に並ぶケースも想定される
- Canvas API水平走査は±5°程度の傾きしか許容できない

これらを踏まえ、検出方式の再検討が必要となった。検出方式（Canvas API vs OpenCV.js）と識別方式（pHash vs テンプレートマッチ）は独立した2軸の選択であることを確認し、OpenCV.js（検出）+ pHash（識別）の組み合わせを提案した。

**回答**: OpenCV.js + pHash を採用（OpenCV.jsのfindContoursで任意角度のパイを検出）

**信頼性への影響**:
- 画像認識アーキテクチャ全体の信頼性レベルが 🟡 → 🔵 に向上
- パイ検出方式が「OpenCV.js findContours」に確定
- パイ識別方式が「pHash（ハミング距離比較）」に確定
- 対応角度が任意角度に拡張
- OpenCV.js WASM ~8MBの先読みロード戦略が確定
- 実装コストが Canvas API 自前実装（~300-400行）から OpenCV.js（~30行）に削減

## ヒアリング結果サマリー

### 確認できた事項
- パイは基本的に横一列に並べて撮影するが、斜め・縦配置にも対応する
- 認識結果は既存のCameraResultとは別画面（`/result` ルート）で表示
- CameraResultは撮影確認用、「認識する」ボタンを追加
- 認識開始はユーザーが明示的にボタンタップ
- manual.pdfは解読済み、加点役の条件タイプが確定
- **スコアリングモデル: yaku配列方式**（各パイがyaku配列を持ち、手牌内での出現回数で判定）
- rules.jsonスキーマ: `[{name, requiredCount, jara}]`
- 加点役は30個以上、requiredCountは加点役ごとに異なる
- ジャラは固定点数の単純合算
- データファイル: pai-details.json, pai-hashes.json, pai-images/
- ルーティング: /, /camera, /result, /rules の4ルート
- **PaiGroup は不要**（yaku配列にグループ情報が含まれるため）
- **CameraMode は `'capture' | 'preview'` の2状態**（認識中はローカル状態、結果は別ルート）
- **MatchedRule.jara は不要**（rule.jara と重複）
- **サービスインターフェースは不要**（DIなしSPAでは過剰）
- **DetectedRegion の imageData は結果に持ち回さない**（パイプライン内部用と結果用で分離）

### 設計方針の決定事項
- 画像認識方式: OpenCV.js（検出） + pHash（識別）
- OpenCV.js WASMはプレビュー画面表示時にバックグラウンド先読みロード
- CameraMode: `'capture' | 'preview'` の2状態
- 認識処理中: CameraResult内のローカル状態 `isRecognizing` で制御
- 認識結果表示: `/result` ルートへのルート遷移
- ルーティング: /, /camera, /result, /rules の4ルート
- パイデータ: `app/static/pai-details.json`（name + yaku配列）
- パイ画像: `app/static/pai-images/`（84枚PNG）
- pHashデータ: `app/static/pai-hashes.json`
- ルールデータ: `app/static/rules.json`（name + requiredCount + jara）
- 新規コンポーネント: `RecognitionResult.svelte`
- 新規サービス: `opencv-loader.ts`, `pai-detector.ts`, `pai-recognizer.ts`, `phash.ts`, `scoring-engine.ts`
- 加点役判定: **yaku配列ベースのルールマッチング**（属性ベースから変更）
- ジャラ計算: 固定点数の単純合算
- **型設計**: サービスIFなし、DetectedRegionは内部用、RecognizedPaiは結果表示用（imageDataなし）

### 残課題
- pHashの精度検証（実際の撮影画像での認識精度テスト）
- 2値化の閾値パラメータ調整
- 画像縮小の最適サイズ確定（精度とパフォーマンスのバランス）
- rules.jsonの30個以上の加点役の具体的な定義作成（TASK-0004）

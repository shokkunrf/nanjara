### Q1: 画像認識アプローチの選択

**質問日時**: 2026-03-13
**カテゴリ**: 技術選択
**背景**: ブラウザ内で動作する画像認識方式として、Canvas API（特徴量マッチング）、OpenCV.js（WASM）、TensorFlow.js（ML）の選択肢がある。パフォーマンス（3秒以内）とデプロイサイズのトレードオフを確認する必要があった。

**回答**: おまかせ（技術的に最適な方式を提案してほしい）

**信頼性への影響**:
- アーキテクチャ設計において認識方式を提案する自由度が確定
- 後続のQ6で最終的に「OpenCV.js（検出） + pHash（識別）」に確定

### Q2: 撮影時のパイの配置条件

**質問日時**: 2026-03-13
**カテゴリ**: データモデル
**背景**: パイ検出アルゴリズムの複雑さは、パイの配置パターンに大きく依存する。自由配置の場合は全面2D探索が必要だが、横一列の場合は水平走査のみで高速検出が可能。

**信頼性への影響**:

- ただしQ6の追加ヒアリングにより、斜め・縦配置への対応も必要と判明

### Q6: 斜め・縦配置への対応

**質問日時**: 2026-03-14
**カテゴリ**: 技術選択
**背景**: Q2で横一列前提としたが、以下の課題が判明した:
- 片手撮影では±15°以上の傾きが発生しうる
- パイが縦に並ぶケースも想定される
- Canvas API水平走査は±5°程度の傾きしか許容できない

これらを踏まえ、検出方式の再検討が必要となった。検出方式（Canvas API vs OpenCV.js）と識別方式（pHash vs テンプレートマッチ）は独立した2軸の選択であることを確認し、OpenCV.js（検出）+ pHash（識別）の組み合わせを提案した。

**回答**: OpenCV.js + pHash を採用（OpenCV.jsのfindContoursで任意角度のパイを検出）

**信頼性への影響**:
- 画像認識アーキテクチャ全体の信頼性レベルが 🟡 → 🔵 に向上
- パイ検出方式が「OpenCV.js findContours」に確定
- パイ識別方式が「pHash（ハミング距離比較）」に確定
- 対応角度が任意角度に拡張
- OpenCV.js WASM ~8MBの先読みロード戦略が確定
- 実装コストが Canvas API 自前実装（~300-400行）から OpenCV.js（~30行）に削減

## ヒアリング結果サマリー

### 確認できた事項
- パイは基本的に横一列に並べて撮影するが、斜め・縦配置にも対応する
- 認識結果は既存のCameraResultとは別画面で表示
- CameraResultは撮影確認用、「認識する」ボタンを追加
- 認識開始はユーザーが明示的にボタンタップ
- manual.pdfは解読済み、加点役の条件タイプが確定
- 各パイに属性（ユニット・学年・誕生月等）を持たせ、属性マッチングで加点役を判定
- 加点役は30個以上、JSONで拡張可能
- ジャラは固定点数の単純合算

### 設計方針の決定事項
- 画像認識方式: OpenCV.js（検出） + pHash（識別）
- OpenCV.js WASMはプレビュー画面表示時にバックグラウンド先読みロード
- 画面遷移: capture → preview → recognizing → result の4状態
- パイ画像配置: `app/static/pais/` に一括配置
- 事前処理データ: `app/static/pais/hashes.json`
- 新規コンポーネント: `RecognitionResult.svelte`
- 新規サービス: `opencv-loader.ts`, `pai-detector.ts`, `pai-recognizer.ts`, `phash.ts`, `scoring-engine.ts`
- 加点役判定: パイ属性ベースのルールマッチング
- ジャラ計算: 固定点数の単純合算

### 残課題
- pHashの精度検証（実際の撮影画像での認識精度テスト）
- 2値化の閾値パラメータ調整
- 画像縮小の最適サイズ確定（精度とパフォーマンスのバランス）
- pais.jsonの属性データ具体的な項目の完全なリスト化
- rules.jsonの30個以上の加点役の具体的な定義作成
